# КВАРТИРА — DESIGN SYSTEM
Версия: 1.0 MVP

## 1. Цель

Создать собственную современную визуальную систему для школы музыки и вокала «Квартира».
Она должна выглядеть как современный продукт 2026 года, а не как шаблон админ-панели.

Основной UX — Mobile First PWA.
Система должна масштабироваться на Tablet/Desktop.

## 2. Визуальное направление

Характер:
- современный;
- музыкальный;
- premium;
- эмоциональный;
- чистый;
- не перегруженный;
- технологичный, но тёплый.

Использовать фирменный логотип школы как главный источник визуального языка.
Не придумывать конкурирующий бренд.

Если логотип доступен в репозитории/assets — использовать его.
Если логотип отсутствует, создать нейтральную временную систему токенов без имитации оригинального логотипа.

## 3. Цветовая система

Не хардкодить цвета по всему проекту.
Использовать design tokens / CSS variables.

Предусмотреть:
- background;
- surface;
- surface-elevated;
- text-primary;
- text-secondary;
- text-muted;
- border;
- brand;
- brand-contrast;
- success;
- warning;
- danger;
- info.

Цвета статусов не должны быть единственным способом передачи информации.

## 4. Типографика

Типографика должна:
- иметь чёткую иерархию;
- хорошо читаться на мобильном;
- иметь крупные заголовки;
- иметь компактные metadata;
- использовать tabular/consistent numerals там, где полезно для времени.

Иерархия:
- Display;
- H1;
- H2;
- H3;
- Body;
- Body small;
- Caption;
- Label.

Не использовать слишком много размеров.

## 5. Spacing

Использовать единую spacing scale.
Не создавать случайные значения margin/padding в каждом компоненте.

Базовый принцип:
- компактные элементы: 4–8 px;
- стандартные: 12–16 px;
- крупные блоки: 20–32 px;
- секции: 32–48+ px.

Точные значения можно адаптировать под выбранный UI framework.

## 6. Радиусы

Использовать единый набор:
- small;
- medium;
- large;
- pill.

Карточки должны иметь современный мягкий радиус.
Не превращать каждый элемент в pill.

## 7. Elevation

Использовать:
- border;
- subtle shadow;
- elevated surface.

Не делать чрезмерные тени.
В тёмной теме глубина может создаваться сочетанием surface и border.

## 8. Навигация

Mobile:
нижняя навигация с 5 основными пунктами:
- Главная;
- Занятия;
- Чат;
- Мероприятия;
- Профиль.

Она:
- фиксированная;
- safe-area aware;
- имеет active state;
- поддерживает badge;
- не перекрывает контент.

Desktop:
допускается переход на sidebar/expanded navigation.

## 9. Кнопки

Варианты:
- primary;
- secondary;
- tertiary/ghost;
- destructive;
- icon button.

Primary CTA должна быть заметной, но не занимать весь экран без причины.

Destructive actions визуально отличаются и часто требуют подтверждения.

## 10. Cards

Карточки использовать для:
- занятия;
- мероприятия;
- преподавателя;
- задания;
- достижения;
- dashboard blocks.

Не помещать в карточку всё сразу.
Принцип: primary information first, secondary details on demand.

## 11. Calendar

Календарь:
- touch friendly;
- легко читаемый;
- не перегружен;
- доступен с клавиатуры на Desktop;
- имеет day/week/month там, где это нужно.

Занятия — визуальные блоки.
Свободные слоты — отдельный понятный интерактивный state.

## 12. Forms

Все формы:
- label;
- helper text при необходимости;
- error state;
- focus state;
- disabled state;
- loading state.

Телефон:
маска/формат +7.
Пароль:
show/hide;
валидация;
понятные ошибки.

Не сообщать лишнюю информацию, которая помогает злоумышленнику угадывать существование аккаунта.

## 13. Чат

UI:
- знакомый messenger pattern;
- собственная визуальная система;
- bubble/message grouping;
- timestamps;
- read status;
- attachments;
- audio player;
- reply/other advanced features only when justified.

На Desktop подготовить split-view.

## 14. Аудио

Аудиоплеер должен быть компактным и современным.
Waveform использовать только если есть смысл.
Touch targets — удобные.

## 15. Notifications

Badge:
- маленький;
- заметный;
- не должен перекрывать иконку.

Toast:
- короткий;
- понятный;
- с action если нужно.

Critical:
- не полагаться только на toast.

## 16. Empty states

Empty state должен объяснять:
1. что сейчас пусто;
2. почему это нормально;
3. что можно сделать дальше.

Пример:
«Пока нет предстоящих занятий»
→ «Найти занятие»

## 17. Error states

Пользовательский текст:
«Не удалось загрузить расписание»
→ «Повторить»

Не показывать stack trace.

## 18. Loading

Предпочитать:
- skeleton для страниц/карточек;
- progress для upload;
- spinner для коротких локальных операций.

## 19. Motion

Анимации:
- короткие;
- функциональные;
- не отвлекающие.

Предусмотреть prefers-reduced-motion.

Использовать motion для:
- появления;
- переходов;
- подтверждения действия;
- drag/interaction только там, где это полезно.

## 20. Accessibility

Минимум:
- WCAG-oriented contrast;
- keyboard navigation;
- visible focus;
- semantic HTML;
- ARIA only when needed;
- labels;
- screen reader text;
- no color-only meaning;
- reduced motion.

Touch target ориентировочно не меньше 44x44 CSS px.

## 21. Responsive breakpoints

Не привязываться к конкретным устройствам.
Использовать content-driven breakpoints.

Принцип:
- mobile: bottom nav;
- tablet: больше пространства, сохраняется знакомый UX;
- desktop: sidebar / multi-column / split view.

## 22. Public screens

Публичная часть:
- сильный hero;
- направления;
- преподаватели;
- мероприятия;
- CTA;
- контакты.

Не делать из неё лендинг из десятков секций.
Она должна ощущаться частью приложения.

## 23. Профиль

Профиль:
- avatar;
- имя;
- role/context;
- важные карточки;
- настройки;
- security;
- help.

Разные роли имеют разные содержательные блоки, но одна визуальная система.

## 24. Принцип качества

Каждый новый UI-компонент должен:
- использовать токены;
- иметь responsive behavior;
- иметь loading/disabled/error состояния, если применимо;
- быть доступным;
- не дублировать существующий компонент.

Не создавать 5 разных компонентов для одной и той же кнопки/карточки.

## 25. Desktop readiness

Даже если MVP проверяется на телефоне:
- компоненты должны иметь desktop variants;
- layouts не должны зависеть от фиксированной ширины телефона;
- tables/calendars/chats должны иметь расширяемую структуру;
- не использовать архитектуру, которая требует переписать navigation после добавления PC.
