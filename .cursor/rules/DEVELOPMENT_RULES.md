# КВАРТИРА — DEVELOPMENT RULES FOR CURSOR
Версия: 1.0 MVP

## 1. Роль Cursor

Работай как senior full-stack engineer + product engineer + UI/UX engineer.

Главная задача:
создать поддерживаемое реальное приложение, а не демонстрационный набор картинок.

## 2. Перед началом

Сначала:
1. прочитай PROJECT_SPEC.md;
2. прочитай DESIGN_SYSTEM.md;
3. изучи весь существующий репозиторий;
4. определи стек;
5. найди существующие routes/components/services;
6. проверь package.json и конфигурацию;
7. только затем планируй изменения.

Если проект пустой — выбери современный устойчивый стек для PWA и объясни выбор в кратком DEV_NOTES.md.

## 3. Не ломать существующее

Если код уже есть:
- не переписывай всё без причины;
- переиспользуй существующие компоненты;
- сохраняй рабочие функции;
- делай небольшие логические изменения;
- после значимых изменений запускай проверки.

## 4. Источник истины

Требования из PROJECT_SPEC.md являются источником продуктовых решений.

Если новое требование пользователя позже противоречит старому:
- новое явно сформулированное требование имеет приоритет;
- обнови документацию;
- не оставляй противоречие в коде.

## 5. Если требование не определено

Не задавай десятки вопросов.

Выбери разумное решение, если:
- оно обратимо;
- не блокирует дальнейшее развитие;
- соответствует UX;
- соответствует безопасности.

Запиши принятое решение в DEV_NOTES.md.

## 6. Архитектура

Разделяй:
- UI;
- business logic;
- API;
- data access;
- auth;
- permissions;
- validation;
- state.

Не помещай бизнес-правила в визуальные компоненты.

## 7. Server-side security

Никогда не считать скрытие UI достаточной защитой.

Все критические права проверяются на сервере:
- просмотр;
- создание;
- редактирование;
- удаление;
- отмена;
- перенос;
- доступ к файлам;
- административные действия.

## 8. RBAC

Использовать централизованную систему ролей/permissions.
Не писать по всему коду:
if user.role === ...

Предпочитать:
can(user, permission)
или аналогичную централизованную систему.

## 9. Lessons / booking

Критическая бизнес-логика:
- сервер проверяет доступность;
- создание записи должно быть атомарным;
- предотвращать race condition/double booking;
- перенос проверяет новый слот;
- отмена корректно освобождает слот;
- важные изменения логируются.

## 10. Validation

Валидировать:
- frontend для UX;
- backend для безопасности и целостности.

Не доверять клиентским данным.

## 11. Forms

Ошибки должны быть:
- конкретными;
- понятными;
- безопасными;
- привязанными к полю, когда возможно.

Не раскрывать внутренние SQL/server errors.

## 12. Authentication

- пароль хранится только в безопасном hash;
- секреты только в environment/secrets;
- не логировать пароли, токены и чувствительные данные;
- session management должен быть продуман;
- logout должен инвалидировать серверную сессию/токен согласно выбранной архитектуре.

## 13. Files

Файлы:
- валидировать MIME/type;
- ограничивать размер;
- генерировать безопасные имена;
- не доверять расширению;
- хранить вне публичного доступа, если контент приватный;
- выдавать доступ через авторизованный механизм;
- предусмотреть антивирусную/контентную проверку как расширяемую часть.

## 14. PWA

Проверить:
- manifest;
- icons;
- service worker;
- installability;
- caching strategy;
- offline state;
- update flow.

Не кэшировать приватные данные без продуманной стратегии безопасности.

## 15. Responsive

Сначала mobile UX.
Но:
- не фиксировать ширины;
- не использовать mobile-only assumptions в core components;
- готовить desktop variants.

## 16. Accessibility

Каждый интерактивный элемент:
- доступен клавиатурой;
- имеет focus;
- имеет accessible name;
- не полагается только на цвет.

Использовать semantic HTML.

## 17. State handling

Каждая серверная операция должна иметь состояния:
- idle;
- loading;
- success;
- error.

Страницы должны иметь:
- loading;
- empty;
- error;
- retry;
- offline, если применимо.

## 18. API

API должен:
- иметь понятные контракты;
- валидировать вход;
- возвращать безопасные ошибки;
- поддерживать авторизацию;
- не отдавать лишние поля.

Если backend пока не готов:
- использовать typed mock/service layer;
- не размазывать mock data по компонентам;
- предусмотреть замену mock API на real API.

## 19. Database

Если база выбирается с нуля:
- использовать нормализованную модель;
- foreign keys;
- indexes;
- timestamps;
- уникальные ограничения там, где нужны;
- audit/history для важных сущностей.

## 20. Testing

Минимум:
- unit tests для критической бизнес-логики;
- integration tests для booking/auth/permissions;
- smoke test основных маршрутов.

Критические сценарии:
1. регистрация;
2. вход;
3. роль;
4. запись;
5. двойная запись;
6. перенос;
7. отмена;
8. доступ к чужим данным;
9. файл;
10. logout.

## 21. Performance

Не оптимизировать преждевременно, но:
- lazy load тяжёлых экранов;
- оптимизировать изображения;
- не тянуть весь чат/расписание сразу;
- использовать pagination/infinite scroll;
- debounce search;
- кэшировать безопасные read-only данные.

## 22. Logging

Логи должны помогать отладке, но не содержать:
- пароли;
- access tokens;
- приватные сообщения;
- секреты;
- ненужные персональные данные.

## 23. UI quality gate

Перед завершением экрана проверить:
- mobile;
- tablet;
- desktop;
- loading;
- empty;
- error;
- disabled;
- keyboard;
- touch;
- long text;
- small screen.

## 24. Не делать fake functionality

Если кнопка существует и выглядит рабочей:
- она должна делать действие;
- либо быть явно обозначена как будущая функция.

Не создавать бесконечные alert('TODO').

## 25. Не усложнять MVP

Не добавлять без необходимости:
- сложную микросервисную архитектуру;
- Kubernetes;
- event-driven инфраструктуру;
- десятки внешних сервисов;
- чрезмерную abstraction.

Архитектура должна быть расширяемой, но простой.

## 26. Документация

После значимых архитектурных решений обновлять:
- DEV_NOTES.md;
- README.md при необходимости.

Не переписывать документацию ради косметики.

## 27. Работа с дизайном

Не использовать случайные UI kits, которые противоречат DESIGN_SYSTEM.md.

Создать переиспользуемые:
- Button;
- Input;
- Modal/Dialog;
- Card;
- Badge;
- Avatar;
- BottomNav;
- Calendar;
- LessonCard;
- MessageBubble;
- AudioPlayer;
- FileAttachment;
- EmptyState;
- ErrorState;
- Skeleton;
- Toast.

Названия можно адаптировать к framework.

## 28. Приоритет реализации

Порядок:
1. foundation;
2. auth;
3. roles/permissions;
4. design system;
5. app shell/navigation;
6. dashboard;
7. lessons/calendar;
8. booking;
9. chat;
10. events;
11. profile/settings;
12. notifications;
13. PWA/offline;
14. educational layer;
15. security/help/public content.

## 29. После каждой крупной фазы

Запусти:
- typecheck;
- lint;
- tests;
- build.

Исправь ошибки до перехода дальше.

## 30. Финальная цель первой итерации

В конце должна существовать запускаемая версия, которую пользователь может открыть и визуально проверить.

Она должна:
- иметь реальную навигацию;
- иметь рабочие переходы;
- иметь роли;
- показывать demo data;
- иметь реалистичные состояния;
- демонстрировать основной flow записи на занятие;
- демонстрировать чат;
- демонстрировать мероприятия;
- демонстрировать профиль;
- работать как PWA;
- быть responsive.

После этого не пытаться самостоятельно бесконечно расширять проект.
Остановиться на стабильной точке и подготовить краткий список:
- что готово;
- что работает на mock;
- что требует backend;
- что является следующим логичным этапом.
